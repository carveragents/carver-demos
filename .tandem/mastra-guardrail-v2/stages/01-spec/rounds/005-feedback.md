## Issues

1. **The new live scoreboard cannot observe the values it scores through `runEvals` on the pinned Mastra version.** The spec says an agent scorer's `output` is the automatic `agent.generate()` result and therefore reads `output.tripwire`, `output.text`, and `output.object` (§12). That is not the `@mastra/core@1.51.0` contract pinned in §15. `runEvals` invokes the agent with `returnScorerData: true`, then calls each scorer with `targetResult.scoringData.output`; `MastraModelOutput.getFullOutput()` defines that field as `ScorerRunOutputForAgent`, i.e. the persisted response-message array. The full result (where `tripwire`, `text`, and `object` live) is available only to `onItemComplete` as `targetResult`. Consequently `unsafeShipScorer`, `stageBScorer`, `guardedCatchScorer`, and `specificityScorer` do not implement the claimed metrics, and V1/V2 remain unclosed in executable form. Redesign only this eval transport boundary: for example, target a thin eval workflow that makes exactly one agent call and returns a normalized delivery result to workflow scorers, or collect full results through `onItemComplete` and compute/assert the named rates from that explicit per-item ledger. Preserve the one-generation-per-item rule, paired population, separate metric polarities, full violated-id attribution, and batch-size breakdown. Pin how subgroup rows are accumulated too: `runEvals` returns averages, not the per-item records the `|candidates|` rows require.

2. **Several adjacent snippets do not type-check against `@mastra/core@1.51.0`; align the spec with the exact dependency rather than describing a nominal API.** In that release:
   - agent defaults are configured with `defaultOptions`, not `defaultGenerateOptions`;
   - structured output is `targetOptions: { structuredOutput: { schema: StageBResponseSchema } }`, not `targetOptions.output`;
   - `createScorer` requires `id` and `description` and is composed with `.generateScore(...)`; `{ name, run }` is not its constructor contract;
   - `RunEvalsDataItem.requestContext` and workflow `run.start().requestContext` require a `RequestContext` instance, so `{ firmProfile: ... }` is not the typed call shown throughout §§10–12; construct `new RequestContext({ firmProfile: ... })` at every programmatic boundary;
   - `instructions`, `tools`, and `maxProcessorRetries` are not the public fields the structural tests read. Use the public async accessors (`getInstructions`, `getModel`, `listTools`, `getDefaultOptions`) where they prove the intended behavior, and/or export and test the single static agent-config object from which both agents are constructed. The test must itself compile and must still fail if either arm becomes request-context-dependent or processor retries return.

   Add a compile/typecheck command to the acceptance path so these contracts are mechanically checked. The official references to pin in the artifact are `https://mastra.ai/reference/agents/agent`, `https://mastra.ai/reference/evals/run-evals`, and the request-context/Studio release note at `https://mastra.ai/blog/changelog-2026-01-30`. This also closes V4/D2's request for actual citations: “verified 2026-07-16” prose without a URL is not a pinned citation.

3. **The negative-control population is still not a closed, reproducible contract.** `NEGATIVE_CONTROL_PROMPTS` is declared as generated and the prose names only three example topics, while the scoreboard and threshold assume exactly ten items. Specify the ten literal prompts or a complete deterministic construction in the winning-scenario table/template fragment, including the invariant that each is an in-scenario benign drafting task and still produces non-empty narrowing candidates under `DEMO_FIRM_PROFILE`. Add a unit test for count, deterministic generation, and those structural invariants. Also name the metric honestly: as currently defined it is a **benign-task pass rate** (a generated draft can unexpectedly violate an obligation), not a ground-truth draft-level false-positive rate. Either keep that label everywhere and stop claiming equivalence to FPR, or judge the underlying blocked/unblocked draft against the candidates and define a true-negative denominator explicitly. In both designs, retain the live `>= 0.9` assertion and the test/proof that an unconditional blocker scores zero.

4. **V9 explicitly requires `candidate_cutoff_date >= MODEL_CUTOFF + 14d`, but the revision implements `+13d`.** The explanation that 13 calendar days preserves the separately locked `2026-03-01` value identifies a real conflict; it does not satisfy the refinement criterion. Resolve it explicitly: implement the required 14-day floor and update affected pool/cost figures, or obtain an orchestrator amendment defining an inclusive-day convention that makes the locked date authoritative. Do not silently substitute 13 for the stated 14-day acceptance condition.
