# Carver × Mastra Compliance Guardrail — goal

Carver × Mastra Compliance Guardrail v1 — a small, self-contained, **public Mastra template** (TypeScript) in which an ordinary business agent with zero regulatory awareness is wrapped in a Carver-powered Mastra **output processor** that blocks, annotates, or passes its drafts against real 2026 regulatory obligations; plus the Python prep pipeline that carves and clears the ~50–200-record canned dataset it ships with. The audience is **Mastra's own team** (template/partnership play). Every canned record must be one where a naked frontier model **provably fails** — proven by an eval harness, not asserted.

## Overall brief (carried into every stage)

**Why this exists.** Mastra's template gallery has research assistants, PDF processors, GitHub PR reviewers, Slack agents and docs chatbots. It has **no compliance or guardrail template, and nothing backed by a real proprietary data feed**. Mastra's processor system (`inputProcessors` / `outputProcessors`, `abort()`/tripwire) is one of the best-built and least-showcased things in the framework. This template fills that gap and makes processors the star. The trade: Mastra gets a category they're missing; Carver gets distribution to every TS dev building agents, and positioning as *the compliance layer under other people's agents* — a far larger story than "Carver has a regulatory search tool."

**The central design fact — where the delta actually lives.** The premise "plug in Carver's data → the agent behaves in a more regulated manner" is only demonstrable where pretraining structurally cannot compete. A frontier model already knows GDPR, MiFID II, the FCA Consumer Duty and Basel III in real depth; ask it a famous-regulation question and Carver adds nothing visible. The delta is real and large in exactly four places:
1. **Recency** — the baseline is `gpt-5.6-sol`, whose knowledge cutoff is **2026-02-16** (verified, OpenAI's own docs); the Carver snapshot runs to **2026-07-11**. Everything published in that ~5-month gap is *structurally* invisible to it. This is the sharpest and most principled selection criterion available — it is not cherry-picking, and the **baseline is deliberately the strongest, newest model available** (see #9), so the delta cannot be dismissed as an artifact of a weak opponent.
2. **Long-tail regulators** — the catalog carries **1,070 bodies**. The model knows the SEC cold; it does not know what the Malta FSA's Banking Supervision Office told Less Significant Institutions, or what Korea's FSS bulletined last quarter.
3. **Exact obligations and dates** — a model confidently emits a *plausible* compliance date. Carver has the extracted one.
4. **Traceability** — Carver carries `reg_references` with real, resolvable EUR-Lex / regulator URLs. The baseline fabricates citations. This is the most demonstrable failure mode in existence.

**A demo built on the wrong questions makes the baseline look fine and Carver look redundant.** Guarding against that is this project's first-order engineering concern, not a polish item.

**What a Carver annotation is.** The AI-generated, deeply-structured intelligence layer Carver's agents attach to one raw regulatory feed entry. Where the raw entry is title + link + date, the annotation is a machine-readable compliance object. Verified paths in `output_data`:
- `scores.{impact,urgency,relevance}.{label,score,confidence}` — impact/urgency each label + 0–10 + confidence; `urgency.basis` (e.g. `past_deadline`). **`relevance` is deprecated — never surface it.**
- `classification.update_type` · `.update_subtype` · `.regulatory_source.{name,division_office,other_agency}` · `.jurisdiction.{scope,country,bloc,locality,region_name,reasoning}` · `.metadata.{title,summary,base_url,feed_url,language}`
- `metadata.impact_summary.{objective,what_changed,why_it_matters,risk_impact,key_requirements[]}`
- `metadata.actionables` — 7 lanes: `policy_change` · `process_change` · `tech_data_change` · `reporting_change` · `training_change` · `status_change` · `other_change`
- `metadata.critical_dates.{effective_date,compliance_date,comment_deadline,early_adoption_date,updated_date,pub_date_content}` each with a paired `*_calendar`, plus `other_dates[]`
- `metadata.reg_references.{rules,statutes,other_ref,personnel,precedents,past_release}` — statutes/rules carry real URLs
- `metadata.impacted_business.{size,type,industry,jurisdiction,other_notes}` · `metadata.impacted_functions[]` · `metadata.penalties_consequences[]` · `metadata.tags[]` · `metadata.entities[]`
- `reconciled_published_date.{date,source,converted,original_calendar,valid}`
- Envelope (siblings of `output_data`): `id` · `topic_id` · `source_id` · `state` · `created_at` · `completed_at`

**The corpus, measured (not assumed).** Snapshot `2026-07-11`, **212,845 records**.
- **The candidate pool is measured, not estimated.** Applying the real filter (#3) — published **2026-03-01 or later** (13 clear days past `gpt-5.6-sol`'s 2026-02-16 cutoff) · actionable `update_type` · `impact_label == "high"` — yields **8,260 candidates**. Against a 50–200-record target that is a **41:1 selection ratio at the top of the range**, ample room to keep only proven baseline failures without cherry-picking.
- That pool by month: Mar 2,200 · Apr 1,950 · May 1,729 · Jun 2,008 · Jul 373 (snapshot ends 2026-07-11).
- That pool by `update_type`: enforcement 2,016 · advisory 1,637 · guidance 1,391 · bulletin 1,235 · final rule 864 · proposed rule 645 · comment request 439 · standard 33.
- That pool by jurisdiction: US 2,393 · FR 929 · CA 368 · CN 353 · AU 258 · DE 236 · GB 234 · IT 208 · CH 196 · NL 155. (EU-member total ≈1,500+ before EU-bloc records — sufficient for scenario A.)
- For reference, looser cutoffs would give 9,998 (Feb 1+) or 11,909 (Jan 1+). **Both are rejected**: they are unsafe against the verified 2026-02-16 cutoff. The ~31% smaller pool is the deliberate price of an unimpeachable baseline.
- **Known corpus rot — handle by construction, not by hope.** 98,826 of 212,845 records are `press release` noise. `reconciled_published_date` spans **1442 → 2569**: date extraction has real garbage (Hijri calendars + bad parses). Never sample randomly; filter hard and hand-review.
- `data/snapshot_meta.json` claims `total_records: 1` against a 212,845-row parquet — **stale/clobbered by a test run. Do not trust it; count from the data.**

**Where the data lives.** The rich fields exist **only** in `../carver-showcase/data/annotations.jsonl` (~1.8 GB, gitignored, one JSON object per line). The published `data/public/annotations.parquet` is an **aggregate-only 15-column bundle with no text at all** (no title, no summary, no actionables) and is useless for this. `../carver-showcase/data/topic_catalog.csv` maps 1,070 bodies (`topic_id,name,acronym,category,class_system,class_sector,class_leaf,tags,jurisdiction_code,jurisdiction_detail,entity_type,govt_body,scope,sectors,industries,functions,legal_instruments,synonyms,constituents,media,hq,base_domain`) and supplies the GICS/Carver-Gov taxonomy from the sibling `gics-topic-tagging` project.

**The publication boundary — understood and deliberately resolved.** `carver-showcase` defends an aggregate-only trust boundary with three enforcement layers (public-build flag, 15-column allowlist, offline leak validator as a blocking gate) and publishes "no raw data, no record-level content." This template is public and is **worthless without record-level content** — titles, `key_requirements`, real citations, `penalties_consequences`. Resolution (**decided by the user, do not relitigate**): a **hand-cleared public set**. The underlying regulator documents are already public; Carver's IP is the *annotation*, and showing a sliver of it is the entire point of a template. Human review of every shipped record IS the clearance gate.

**Locked decisions (do not relitigate):**
1. **Two halves, one seam.** `prep/` = Python 3.10, carves + clears the dataset, never ships. `template/` = TypeScript Mastra template, **self-contained with the cleared JSON vendored in**, runnable from a fresh clone with only `OPENAI_API_KEY` — no Carver API key, no network, no dependency on `prep/`, `carver-showcase`, or this repo. It must be **trivially extractable into its own repo** if Mastra wants to host it.
2. **The dataset is selected by measured baseline failure, not by taste.** The pipeline is `candidates → cold baseline model → score vs Carver ground truth → keep ONLY failures → human review → cleared set`. A record enters the set **only** with recorded evidence of how the baseline failed it (fabricated citation / wrong compliance date / missed obligation). This is the project's defining constraint.
    - **Score deterministically wherever the check is deterministic — do NOT reach for an LLM judge by default.** "Fabricated citation?" = extract citations/URLs from the baseline answer, check against the record's `reg_references`, and resolve over HTTP. "Wrong compliance date?" = compare against `metadata.critical_dates.compliance_date`. These are string and HTTP checks: free, reproducible, and unarguable in a way a judge's opinion is not. **Only irreducibly fuzzy checks** (e.g. "did it miss the obligation entirely?") may use an LLM judge, and that judge runs on OpenAI (see #9).
3. **Candidate filter:** published **2026-03-01 or later** · actionable `update_type` (per the list above; never `press release`/`other`/`speech`/`event announcement`/`newsletter`/`insights`/`trend report`) · `impact_label == "high"` · `reconciled_published_date.valid == true` and parseable · non-empty `impact_summary.key_requirements` · `reg_references` carrying at least one **resolvable** URL. **Measured pool: 8,260 candidates.**
    - **Why a margin at all.** A February-1 filter would admit Feb 1–15 documents that may sit *inside* the model's training data, silently corrupting the experiment. **2026-03-01 is 13 clear days past the 2026-02-16 cutoff** — an indisputable margin. The margin exists to absorb uncertainty in the provider's stated cutoff and publication-date skew; 13 clear days does that as completely as 14 would.
    - **The derivation is the rule; the date is its output.** Enforce the *derivation* mechanically — `load_settings()` asserts `candidate_cutoff_date >= MODEL_CUTOFF + margin`, with the margin convention **named explicitly at the constant, in the function, and in a test**. Do **not** enforce a hardcoded literal: a bare floor independent of `MODEL_ID` is exactly the hole that would let a model swap silently corrupt the filter. (The spec implements this as `CUTOFF_MARGIN_DAYS = 14` under an explicitly-named **inclusive** convention — counting the cutoff date as day 1, Feb 16 → Mar 1 is 14 days — which reproduces `2026-03-01` exactly. Any convention is acceptable provided it is named, tested, and derives the date from `MODEL_CUTOFF` rather than hardcoding it.)
    - **ORCHESTRATOR NOTE (2026-07-16) — an amendment issued and then WITHDRAWN; recorded so it is not re-litigated.** This decision's earlier prose called 2026-03-01 "a clean, indisputable two-week margin" without naming a counting convention. Refinement 1 read that as 14 *clear* days and demanded `+14d`, which yields 2026-03-02 and would have moved this locked date. The maker correctly **refused to move a locked decision unilaterally**, implemented the inclusive reading, and flagged the conflict for the orchestrator instead of silently choosing — the right call, and the reason this was caught. On review the maker's reading is also the better one: goal #3's own prose and its own number are consistent *only* under the inclusive convention, so there was never an arithmetic error to fix — only imprecise wording, now fixed above. **The `2026-03-02` / 8,199 amendment is withdrawn. `2026-03-01` and the measured 8,260 pool stand.** Chasing 2026-03-02 would have cost 61 records (0.74%) and ~10 figure updates across the spec to fix a wording problem, not a safety one.
    - **If the model in #9 ever changes**, the date is re-derived from the new model's documented cutoff via the same named margin rule. Tighten if the new cutoff is later; **NEVER loosen it to grow the pool.**
    - The cutoff is a **heuristic for picking the candidate pool only**. Membership in the cleared set is decided by **measured failure** (#2), never by the date. A wrong cutoff therefore costs *yield*, not *validity* — and thin yield is handled by #11 (ship smaller; never loosen).
4. **The probe IS the scoreboard.** The same scorers that curate the set ship as the eval harness. Do not build two harnesses. This makes proof a by-product of curation.
5. **The guardrail = a Mastra `outputProcessor`, in three stages.** (a) **Deterministic narrowing** — filter the cleared set by firm profile (jurisdiction, sector, `impacted_functions`) to a handful of candidate obligations; no LLM, fast, explainable. (b) **LLM verdict** — the pinned model (#9) judges the draft against only those candidates, returning a Zod-typed structured verdict. (c) **Enforcement**.
6. **Severity comes from Carver's own `impact_label`, never from a hand-invented rule.** `high` → `abort()` (hard tripwire, visible in Studio). `medium` → annotate + warn. `low` → pass. That the *data* sets the threshold is the argument that Carver does work a prompt cannot.
7. **No RAG. No vector store. No embeddings.** ~200 records is a JSON file plus deterministic filter tools (`createTool`, Zod schemas). No second API key and nothing to flake on stage. LibSQL is available if it ever needs scale; it does not now.
8. **Two surfaces, split by what each is good at. Build no custom frontend, no server, no SPA.**
    - **Studio shows the MECHANISM.** `mastra dev` → `http://localhost:4111`. A **comparison workflow** (`createWorkflow` + `.parallel([baselineStep, guardedStep])` → `reportStep`, registered via `new Mastra({ workflows: { compareWorkflow } })`) runs the same prompt through the unguarded and guarded agents. Studio auto-discovers registered workflows — there is **nothing to build for Studio itself** — and renders the run as a live graph: one branch completes, the other tripwires, with traces showing the processor firing and which Carver record matched. This is the surface that flatters Mastra's own machinery, which matters because Mastra's team is the audience.
    - **A generated static HTML report shows the CONTRAST.** `npm run demo` executes the same workflow and emits a **self-contained HTML file** (inline CSS, no external assets, no server, no framework) with the two drafts side by side, the Carver obligation that fired, its resolvable citation, and the compliance date. It is a **build artifact, not an app** — shareable with Mastra without them running anything. This follows the established house pattern: `carver-showcase` builds a PDF deck from real data via `tools/build_deck.py`; `gics-topic-tagging` ships `slides/carver_taxonomy_v1.html`.
    - **Why both:** Studio's workflow output renders as **JSON**, not formatted prose, so it cannot show a readable side-by-side of two drafts; Studio's agent chat renders markdown but has no flow visualization. Neither surface does both. The split is deliberate — do not try to collapse it into one.
    - **KNOWN RISK — resolve empirically before building on it.** `agent.generate()` returns `result.tripwire` rather than throwing (verified). It is **NOT verified** whether a tripwire raised inside a `.parallel()` step propagates up and ends the whole workflow run in `tripwire` status — Mastra's workflow status union does include `tripwire`, so this is plausible. If it propagates, it would kill the baseline branch and break the comparison. **Mitigation:** catch the tripwire inside the guarded step and return a structured `{ blocked: true, reason, processorId, record }`, keeping the run in `success` with both branches intact. Verify this in the first hour of the template stage; do not assume either way.
9. **Model = `openai/gpt-5.6-sol`, via Mastra's model router string form.** Key `OPENAI_API_KEY`. Use `provider/model` (slash), never `provider:model`. Do **not** install an AI SDK package. Pin the model id in **one** config constant shared by both halves.
    - **Verified facts (OpenAI's own docs + Mastra's provider catalog, checked 2026-07-16):** `gpt-5.6-sol` is OpenAI's **current flagship** — *"If you're not sure where to start, use GPT-5.6 Sol, our flagship model for complex reasoning and coding."* Knowledge cutoff **2026-02-16**. Released ~2026-07-09 (press-sourced; the cutoff is doc-sourced and is the load-bearing fact). Valid Mastra router string: **`openai/gpt-5.6-sol` — the explicit id, and ONLY the explicit id.** (Mastra also accepts the bare alias `openai/gpt-5.6` → Sol. **This project rejects it — see D17.** An alias's *target* changes; pinning a knowledge cutoff to an alias is a time bomb that passes every check the day it re-points.) Mastra confirms *"Authentication is handled automatically using the `OPENAI_API_KEY` environment variable."*
    - **Why the flagship and not an older, weaker model.** The temptation is to pick an early-cutoff model to maximise the post-cutoff window and harvest more failures. **That is rigging, and it is forbidden.** "You benchmarked against an old model" is the one question that kills this artifact, because the claim is about Carver, not about model age. The strongest baseline makes the strongest demo: *even OpenAI's newest flagship, released days earlier, confidently fabricates this citation.* The price is a 31% smaller pool (11,909 → 8,260), which #3 shows is still a 41:1 selection ratio. **Pay it.**
    - **State the baseline model and its cutoff plainly in the template README and in the HTML report.** Transparency is the defence against the cherry-picking charge; hiding it invites the charge.
    - **THE ANTHROPIC API IS OUT OF SCOPE — user directive, do not relitigate.** No `ANTHROPIC_API_KEY`, no `anthropic/*` model string, no `@ai-sdk/anthropic`, no Claude API call from `prep/` or `template/`, anywhere, for any purpose. (This constrains only what the *built artifact* calls. The coding agent building this project is itself Claude and its own reasoning is unaffected — where a judgment can be made inline by the agent at build time instead of by an API, prefer that.)
    - **THE EXPERIMENT IS CONTROLLED: baseline and guarded MUST be the identical model with identical config, differing ONLY in whether Carver data is present.** This is the entire basis of the project's claim, and it is **provider-agnostic** — OpenAI on both sides is exactly as valid as any other pairing. What is fatal is a *mismatch*: probing with one model and demoing with another silently measures a **model comparison** and reports it as Carver's contribution. It would *appear* to succeed, which is what makes it dangerous. The `prep/` probe and the template's guarded agent read **the same pinned model constant**.
    - **The model id is a template config constant, not a hard dependency.** Mastra's router makes the provider a string, so anyone forking this (including Mastra) can swap providers by editing one line. Say so in the template README. We build and verify on OpenAI because that is the key we have.
    - The **only** secret this project needs, in either half, is `OPENAI_API_KEY` (in `prep/.env` and `template/.env`, both gitignored). No Carver key. No Anthropic key. No Mastra key or account — Studio is the local, open-source (Apache-2.0) dev UI started by `mastra dev`; **Mastra Platform (`projects.mastra.ai`, the paid hosted product, opt-in via `MASTRA_PLATFORM_ACCESS_TOKEN`) is explicitly OUT of scope — never sign up for it, never set that token.**
10. **Scenario is decided by the probe, once, at the end of the prep stage — then built once.** Two candidates: **(A)** a coding/product agent tripping the **EU AI Act + GDPR**; **(B)** a marketing agent tripping **financial-promotion rules**. Whichever yields more and stronger *documented* baseline failures wins. **Tie-break → (A)**: the audience is developers. **Do not build both. Do not stall on this.**
11. **Cleared set = 50–200 records — a TARGET, never a quota.** Every record human-reviewed, tracked in git under `data/cleared/`. Candidates, probe runs and logs go to `data/scratch/` (gitignored).
    - **The filter (#3) is a floor and is NEVER relaxed. The set size is a ceiling and may be freely reduced.** If the probe yields fewer survivors than hoped, **ship the smaller set and report the true number.** A 30-record set of proven baseline failures is a success; a 200-record set padded with records the baseline handles competently is a **failure**, because it destroys the one claim the template exists to make.
    - **Explicitly forbidden ways to "hit the number":** loosening the date cutoff, admitting `medium`/`low` impact, admitting noisy `update_type`s, accepting unresolvable citations, waiving human review, weakening the failure bar so near-misses count, or synthesizing/paraphrasing records. If the yield is thin, that is a **finding to report prominently**, not a problem to engineer around.
    - No minimum is imposed. If fewer than ~20 records survive, ship them, say so plainly in the findings, and let the user decide — **do not pad, do not relax, do not substitute.**
12. **Stack.** `template/`: TypeScript, **Node ≥ 22.13.0**, ESM-only (`"type": "module"`), `tsconfig` `module`/`moduleResolution` must be modern (`ES2022`/`bundler` — CommonJS breaks Mastra resolution), `@mastra/core`, `zod@^4`, Vitest.
13. **All Python runs in an isolated, project-local virtual environment. No exceptions.**
    - The venv lives at **`projects/mastra-guardrail/prep/.venv`**, created with `python3.10 -m venv .venv`, and is **gitignored**. Dependencies are declared in `prep/requirements.txt` (runtime) and `prep/requirements-dev.txt` (test/dev), per this repo's convention.
    - **Never** `pip install` into system/global Python. **Never** reuse or write to `../carver-showcase/.venv` or any other project's venv. **Never** import the `carver_showcase` package (different repo, different venv, Python 3.12).
    - `prep/` reads the JSONL as a **standalone streaming reader** — one JSON object per line, never load 1.8 GB into memory.
    - Every documented command is invoked through the venv explicitly (`.venv/bin/python …`), run from `prep/`, exactly as the sibling `gics-topic-tagging` project does.
14. **Scoreboard ships as `npm test`** — `runEvals()` from `@mastra/core/evals` under Vitest, baseline vs guarded, side by side. Mastra's team must be able to verify the claim in one command; for this audience that is worth more than any slide.

**Hard constraints (do not violate):**
- **`../carver-showcase` is READ-ONLY.** Never write to it, never modify its pipeline, never touch its trust boundary or validators.
- **Never ship a record that has not been human-reviewed.** Human review is the publication gate; there is no automated substitute.
- **Never ship a fabricated, paraphrased or synthesized record.** Real annotations only — fake citations in a demo whose entire point is real citations would be fatal. If a citation URL does not resolve, the record is out.
- **Never surface `relevance`** (deprecated weighted sum) or **topic categories** anywhere externally.
- **Secrets in a git-ignored `.env`** inside the project folder. Never commit keys. `OPENAI_API_KEY` only; no Anthropic key, no Carver key, no Mastra token.
- **This project needs its own `projects/mastra-guardrail/.gitignore`.** The repo-level one predates any TypeScript work and covers only `.venv/` · `.env` · `__pycache__/` · `dist/` · `output/` · `logs/`. It has **no `node_modules/`**. The project-local ignore must cover at minimum: `node_modules/` · `.mastra/` · `data/scratch/` · `prep/.venv/` · `.env`. `data/cleared/` is **tracked** — it is the deliverable.
- **Commit as you go; NEVER push.** Commit at meaningful checkpoints on a work branch. **No `git push`, no PR, no remote interaction of any kind** — the user integrates via their own flux workflow. Never commit secrets, `node_modules/`, the venv, `data/scratch/`, or anything from `../carver-showcase`.
- **Per this repo's CLAUDE.md:** TDD before implementation · right-sized models per task · run the python-code-reviewer agent after each Python change and have the python-expert fix findings · each project self-contained under `projects/` with its own README · record non-obvious learnings in `docs/LESSONS.md` and add a row to the root README's Projects table.

**Success criteria (all must hold):**
1. From a fresh clone of `template/` with only `OPENAI_API_KEY` set: `npm install && npm run dev` serves Studio on `:4111` with no further setup.
2. A scripted demo prompt makes the guarded agent produce a **visible tripwire block** in Studio, citing a real Carver obligation with a **resolvable** URL and a real compliance date.
3. The same prompt against the unguarded baseline produces **visibly non-compliant output** — ideally with a fabricated citation.
4. The **comparison workflow appears in Studio** without any Studio-specific code, and a single run visibly executes **both** branches to completion — the guarded branch blocked, the baseline branch not — in one graph. A tripwire must **never** abort the run or kill the baseline branch.
5. **`npm run demo` emits a self-contained HTML report** that opens directly in a browser with **no server and no network** (inline CSS, no external assets), showing the two drafts side by side plus the Carver obligation that fired, its clickable citation, and the compliance date. It is generated from a **real run**, never hand-authored.
6. `npm test` runs the evals and prints a baseline-vs-guarded scoreboard with a **material, reproducible gap**.
7. Every record in `data/cleared/` carries recorded baseline-failure evidence and a human-review sign-off.
8. Every citation URL in the cleared set resolves.
9. `template/` has zero references to `prep/`, `carver-showcase`, or anything else in this repo.

**North star:** a Mastra developer watches a perfectly ordinary agent confidently ship something that breaks a real 2026 regulation, then watches the same agent stopped cold — with a citation they can click and a date they can check. They think *"I want this under my agent."* Everything in this project serves that ten seconds; anything that doesn't is out of scope.
